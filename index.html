AI 自进化项目 · Bug Hunter

会从 PR 结果里改写打法的捉虫机器人

Bug Hunter 每天在 GitHub 仓库里找 Bug 和改进机会：读代码、Issue 和测试，判断项目最需要什么，核对证据，动手修改并跑测试，产出待审核的补丁或 PR。每一次合并、关闭、团队投票都会被折算成奖励，用来改写它下一次挑仓库、挑方向、找 Bug 和写 PR 的方式。

自动化让它每天都跑；自进化让它每天跑得不一样——而且每次改变都要拿真实结果证明更好。

目标与赛道

为谁变得更好？

目标决定“什么算好结果”。三个目标按权重同时进化；项目类型只是初始猜测，不是写死的规则。

contributor

拿到更多被合并的贡献

学习什么样的仓库维护者更愿意回复和合并外部 PR，什么样的 PR（小 Bug、小功能）更容易进。

craft

提高修 Bug 的能力

总结哪里最容易出 Bug、什么 Bug 该怎么修、诊断为什么会被推翻，把经验喂回下一次诊断和修复。

internal

让内部工具更好用

团队工具多是 AI 辅助写出来的：更需要准确、快速、轻便和代码瘦身，而不是无限加功能。团队投票就是奖励。

自动化（每天照常跑）

选仓库 → 侦察 → AI 诊断 → 证据核对 → 修复并测试 → 待审核 PR → 记录。连续 30 天做同样的事，只是数据变多。

自进化（每天跑得不一样）

第 30 天挑的仓库、选的方向、写 PR 的方式都和第 1 天不同，并且能指着真实结果说明为什么改、改完好了多少。

自动化层

每日狩猎流水线

Cron 每 20 分钟推进一步，每天完成一轮。白色步骤在 Cloudflare 上完成；浅紫色步骤由执行器完成，因为 Worker 不能克隆仓库、不能跑测试。

挑仓库

内部仓库全看；开源仓库按冠军打法打分，少量名额留给挑战者和随机探索。

侦察

读取元数据、README、根目录、开放 Issue、最近关闭的 PR，算出仓库画像和特征。

AI 诊断

结合打法里的类型偏好和经验，判断项目痛点，给出 ≤3 个带证据的机会；无密钥时按 Issue 标签回退。

证据核对

文件是否存在、Issue 是否开放、是否已被认领或已有 PR。模型的话不算证据。

复现与修改

执行器领任务、克隆、跑基线测试，按经验生成最小改动。

测试

跑仓库自己的测试；失败带日志重试一次，仍失败就记录原因。

待审核

补丁和 PR 描述存档；人工审核后才提交，只读仓库永不提交。

收集反馈

轮询 PR 合并/关闭/无人理睬，接收团队投票，折算奖励，触发进化。

⇄

大脑与双手：Worker + D1 负责决策和记账；执行器（本地、GitHub Actions 或 Agent）通过 /api/queue 领任务、通过 /api/attempts 回传补丁和测试日志。

自进化层

打法手册如何长出新枝

每个机会在决策时都拍下快照：仓库特征、画像、类型、所用打法版本。结果回来后折算奖励，统计学习和 AI 反思一起生成候选打法，再用历史证据比较新旧。

四个进化维度：每一个都是可调整的偏好，而不是固定规则。
维度要回答的问题打法里可调的部分学习信号
E1 挑仓库哪些仓库的维护者更愿意回复、合并外部 PR？仓库特征权重、发现仓库的搜索式PR 合并 / 关闭 / 超时无人理睬
E2 挑方向什么类型的项目最需要哪类改动？项目画像 × 机会类型偏好（Bug、准确、速度、瘦身、UI、小功能、竞品缺口）验证通过率、修复成功率、接受率
E3 找和修哪里容易出 Bug？什么 Bug 怎么修？找 Bug 经验（带证据编号），注入诊断和执行器提示词测试通过 / 失败、诊断被推翻
E4 写 PR怎样的 PR 更容易被合并？写 PR 经验、改动行数上限、是否先开 Issue合并、关闭、维护者评论

结算奖励

按目标组合折算：合并 +1、关闭 −0.5、团队说有用 +1（内部）……没结果的不参与学习。

生成候选

特征权重做带锚点的回归，类型偏好做贝叶斯更新；AI 反思提出经验，必须引用真实结果编号。

离线回放

训练集拟合、保留集评估：“如果当初用新打法排序，排在前面的机会奖励更高吗？”

晋级或 A/B

明显更好就晋级；分不出高下就当挑战者，拿 30% 名额线上对比；更差就淘汰，但保留在树上。
